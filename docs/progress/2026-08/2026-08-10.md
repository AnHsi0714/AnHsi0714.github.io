### AI／搜尋引擎爬蟲可讀性：新增 headless-browser prerender

使用者貼了一份他看過的外部分析，指出網站目前是純 client-render 的 SPA，crawler 直接 `GET /about`、`GET /projects/personal-website` 這類路由會拿到 GitHub Pages 原生 404（連 JS 都還沒機會執行），問能不能讓 AI 只丟首頁網址就能沿著 Navbar 讀到完整內容。逐項對照 repo 驗證這份分析：`index.html` 確實只有空的 `<div id="root">`，沒有 `public/404.html` 這種 SPA fallback，[router.tsx](../../../src/router.tsx) 的路由跟外部分析列的完全對得上，內容本身（`content/*.json`、`content/{projects,articles}/{zh,en}/*.md`）已經整理得很好，純粹是建置/部署流程的問題。

新開分支 `feat/seo-prerender`，先用兩個 Explore agent 平行摸清楚每個內容區塊的資料來源與語言判斷邏輯（[projects.ts](../../../src/lib/projects.ts)、[articles.ts](../../../src/lib/articles.ts)、[knowledge.ts](../../../src/lib/knowledge.ts) 都用 `import.meta.glob(eager:true)`，是 Vite-only 功能，一般 Node script 裡跑不起來）、[LanguageContext.tsx](../../../src/context/LanguageContext.tsx) 的預設語言邏輯（讀 `localStorage`，沒有值時預設 `zh`）、[Friends.tsx](../../../src/pages/friends/Friends.tsx) 對 Supabase 的即時資料依賴，再進 Plan Mode 對齊方案。

決定採用 headless browser（Playwright）在 `vite build` 後做靜態快照，而不是改寫成 SSR／換 Next.js：站上有好幾個頁面重度依賴瀏覽器環境的 canvas（p5.js 手繪作品、`@react-three/fiber`／three.js、matter-js），目前完全沒做 SSR-safe 處理，改寫成 `react-dom/server` 相容要包一層防護、改動面大又沒有實質好處（canvas 內容本來就無法在伺服器端有意義地渲染）；用真的 headless Chromium 直接跑已經能動的 production bundle，App 程式碼完全不用為了「SSR 相容」而改。

新增 [scripts/prerender.ts](../../../scripts/prerender.ts)：用 Vite 的 `preview()` API 在本機把 `dist/` 服務起來，開一個 Playwright headless Chromium 依序造訪靜態路由（`/`、`/about`、`/projects` 等）與動態路由，把渲染完的 DOM 存成 `dist/<route>/index.html`。動態路由的 slug 清單直接用 `fs` 讀 `content/*.json`／掃 `content/articles/zh/**/*.md`（重用 [markdown.ts](../../../src/lib/markdown.ts) 的 `parseFrontmatter` 過濾 `status: draft`），不呼叫那些依賴 `import.meta.glob` 的既有 loader；`/friends`、`/friends/create`（Supabase 即時／純寫入頁面）跟 `/dev/*`（內部預覽頁）刻意排除在外。同一份路由清單也拿來產生 [`dist/sitemap.xml`](../../../scripts/prerender.ts)，另外新增 [public/robots.txt](../../../public/robots.txt) 指向 sitemap。

順手修了一個發現到的既有缺口：全站每個路由渲染出來的 `<title>` 都共用 `index.html` 裡那個固定的「AnHsi0714」，沒有任何頁面設定過 `document.title`。新增 [useDocumentTitle.ts](../../../src/hooks/useDocumentTitle.ts)（設定 `document.title` 跟 upsert `<meta name="description">`），接到 About／Projects／ProjectDetail／Articles／ArticleDetail／Knowledge／KnowledgeDetail，讓 Playwright 快照跟一般 SEO 都能拿到有意義的每頁標題與摘要（長文字用既有的 `deriveExcerpt()` 截斷）。

`package.json` 新增 `playwright`、`tsx` 兩個 devDependency，`build` 改成 `tsc --noEmit && vite build && npm run prerender`；[deploy.yml](../../../.github/workflows/deploy.yml) 在 `npm ci` 後、`npm run build` 前加一步 `npx playwright install --with-deps chromium`。

本機跑 `npm run build`：79 個路由全部成功產生快照，兩篇草稿文章正確被排除在 `dist/articles/` 跟 sitemap 之外。驗證過程中一度誤判修復無效：用 `vite preview` 測 `curl /about`（無結尾斜線）時 fallback 回首頁殼，後來確認是 `vite preview` 的 SPA fallback 邏輯跟真實靜態主機的 clean-URL 解析規則不同；換成 `npx serve dist`（比較貼近 GitHub Pages 之類靜態主機的解析行為）重測，`GET /about` 直接 200 拿到完整渲染內容跟正確的 `<title>`，才確認 `dist/<route>/index.html` 這個結構本身是對的，快照裡的 `<script>` 也仍指向正確的 hashed bundle，人類訪客照常能拿到完整互動的 SPA。
### 文章新增「上一篇文章」導覽

參考既有的「下一篇文章」，[articles.ts](../../../src/lib/articles.ts) 新增 `usePreviousArticle(slug)`。原本 `useNextArticle` 是「先看 frontmatter 手動指定的 `nextSlug`，沒有才 fallback 回日期排序的下一筆」，如果「上一篇」單純用日期排序回推一筆（`index - 1`），遇到像 `exploring-hci` 這種手動指定 `nextSlug` 打亂日期序的系列文章就會兩邊對不起來（A 的下一篇手動指到 C，但 C 的上一篇卻演算成別篇 B）。改成抽出共用的 `effectiveNextSlug()` 算出每篇文章「實際的下一篇」，`usePreviousArticle` 反查「誰的下一篇指向我」，兩個方向永遠對稱。[ArticleDetail.tsx](../../../src/pages/articles/ArticleDetail.tsx) 上下篇排版原本是 50/50 兩欄，後面因為要塞進「回列表」變成三欄（見下一則）。

### 詳情頁「回列表」連結重新設計：從頭到尾都在同一個位置

過程整理如下（依實際迭代順序）：

1. **先加底部連結**：使用者反映讀完長文章要往上捲回頁首才能點「回列表」，[ArticleDetail.tsx](../../../src/pages/articles/ArticleDetail.tsx)／[ProjectDetail.tsx](../../../src/pages/projects/ProjectDetail.tsx)／[KnowledgeDetail.tsx](../../../src/pages/knowledge/KnowledgeDetail.tsx) 底部都加上跟頂部一樣的「回列表」`TextLink`（帶 `restoreScroll`）。
2. **目錄側欄改成同時支援專案頁、並內嵌回列表**：使用者接著要求「有目錄就不用上方 link」，因為左側 `TableOfContents` 側欄本身也能放回列表連結、且滑動內容時永遠在畫面上。[TableOfContents.tsx](../../../src/components/TableOfContents.tsx) 新增 `backLink` prop，放在浮動側欄最上方；[ArticleDetail.tsx](../../../src/pages/articles/ArticleDetail.tsx) 原本只有 `headings.length > 1` 才渲染 TOC，改成一律渲染（沒標題時側欄只顯示回列表，不顯示可收合的標題清單）；[ProjectDetail.tsx](../../../src/pages/projects/ProjectDetail.tsx) 也比照加上目錄支援（新增 `t.projects.tableOfContents` 中英文案）。
3. **修正頂部/底部連結顯示邏輯，改用斷點而非 JS 完全關閉**：側欄只在 `2xl`（≥1536px）才顯示，如果直接用 `hasToc` 這個 JS 布林值整個關掉頂部/底部連結，窄螢幕、平板會變成「有目錄的頁面完全找不到回列表」。改成套用 `2xl:hidden` 這個 CSS class，只在側欄真的會出現的寬螢幕才隱藏，窄螢幕維持顯示。
4. **底部連結加上「只在真的需要捲動時才顯示」的條件**：沒有目錄的頁面（或知識點頁，本來就沒有目錄功能）如果內容很短、根本不用捲動，同時看到頂部跟底部兩個一樣的連結會很怪。新增 [useNeedsScroll.ts](../../../src/lib/useNeedsScroll.ts)，量測 `document.documentElement.scrollHeight > window.innerHeight` 決定要不要顯示底部連結。第一版掛 `ResizeObserver` 在 `document.documentElement` 上想抓圖片/影片載入後的高度變化，但 `<html>` 本身的框高被視窗釘住，內容變高不會讓它自己的 box 尺寸改變，觀察不到，導致底部連結在手機、平板上幾乎永遠不出現；改觀察 `document.body`（一般文件流下高度真的會隨內容變化）並補上 `load` 事件監聽才修好。
5. **底部連結併入上下篇文章那一列，並用 grid 讓它真正置中**：使用者建議與其獨立一整行,不如把回列表放進上一篇／下一篇中間,原本 50% 兩欄改窄一點。第一版用 flex 排版,結果「只有下一篇、沒有上一篇」時,回列表因為是 flex 裡第一個子元素,直接卡在最左邊而不是正中間。改成 CSS Grid 三欄（`grid-cols-3`）,上一篇／回列表／下一篇分別釘在第 1／2／3 欄的固定位置,不管旁邊的欄位存不存在,回列表永遠在正中間；`hasToc` 時 `2xl` 以上回列表整欄隱藏,grid 同時縮回兩欄讓上下篇補滿回一半寬。

### 瀏覽軌跡（Trail）功能

新增 [TrailContext.tsx](../../../src/context/TrailContext.tsx)：用 `sessionStorage` 記錄最近 4 站瀏覽紀錄（關分頁就重置，符合「這次逛到哪」的直覺）。三個操作分開設計，行為容易搞混，中間修正了兩次：

- `pushTrailEntry`：一般內容連結（相關文章／知識點 chip 等）點進詳情頁都走這裡，單純累加、不去重複比對——第一版做成「同一站再點就移到最後面」，結果 A、B 互相連結時（很常見，文章跟對應知識點常常互相連回去）來回點兩下軌跡就被誤判成「回到分岔點」打回 1 筆而整條消失，改回單純累加才符合「A→B→A 應該是三站」的要求。
- `jumpTrailTo`：只有直接點擊軌跡列本身的某一站才走這裡，把後面沒逛過的路徑截斷。
- `clearTrail`：離開文章／專案／知識點詳情頁（回列表、去別的分類、回首頁……）代表一次瀏覽流程結束，軌跡歸零；判斷邏輯放在 [App.tsx](../../../src/App.tsx) 用路徑正則比對，不是個別頁面各自處理。

三個函式都用 `useCallback` 包成穩定參照（內部都是 `setTrail(prev => ...)` 函式式更新，不 closure 任何會變的外部值），呼叫端的 `useEffect` 才能誠實列出完整依賴陣列，不用靠 `eslint-disable` 蓋掉「少列依賴」的警告。

新增 [Trail.tsx](../../../src/components/Trail.tsx) 渲染成「A › B › C」，最後一個（目前頁）不是連結，並整合進三個詳情頁。上線後發現主控台噴 `Encountered two children with the same key`：軌跡設計上允許同一頁非連續出現兩次（A→B→A），這種情況兩個節點的 `path` 會相同，用 `item.path` 當 React key 就會撞號，改用 `item.trailIndex`（陣列裡的實際位置，保證唯一）解決。
