### 除錯：目錄點擊沒有跳轉——StrictMode 下 render 時遞增的計數器失準

功能做完後使用者實測回報「點目錄標題沒有真的跳轉」，且「有些標題有 id、有些沒有，有 id 的也對不上標題文字」。一開始懷疑是原生 `<a href="#id">` 錨點跳轉在這個 SPA 版面下不可靠（React Router 的 `BrowserRouter` 不一定會把純錨點的 fragment 導覽當成一次 location 變化），先把 [TableOfContents.tsx](../../../src/components/TableOfContents.tsx) 的點擊行為改成主動抓 DOM 元素呼叫 `scrollIntoView`，同時保留修飾鍵點擊開新分頁的原生行為——但這只讓「跳轉動作」更可靠，沒解決「id 對不上」這個更根本的問題，使用者重測後問題依舊。

追出真正原因：[main.tsx](../../../src/main.tsx) 有包 `<StrictMode>`，React 18 開發模式下會把每個元件的 render 函式故意呼叫兩次來抓不純的 render。原本 `MarkdownContent.tsx` 的標題 renderer 用一個 `useRef` 計數器在渲染每個標題時 `+= 1`，藉此對應 `extractHeadings()` 算出的第幾個標題——這是在 render 過程中做 side effect 式的狀態變動，StrictMode 重複呼叫時計數器被多加，後面所有標題的對應就整個錯位、部分甚至超出陣列範圍變成 `undefined`，正好吻合回報的症狀。

改成不依賴任何跨節點的共用計數器：每個標題的 `id` 直接由「自己渲染出來的文字」現算（新增 `headingToPlainText()` 把巢狀 React 節點攤平成純文字，再丟進 `slugifyHeadingText()`），是個純函式，呼叫幾次結果都一樣，天生免疫 StrictMode 的重複呼叫。`extractHeadings()` 也同步拿掉原本「同名標題加序號消歧」的邏輯，改成單純用同一顆 `slugifyHeadingText()` 算 id，確保左側目錄跟正文標題永遠用同一套邏輯對得上——原本用計數器對應「第幾個標題」的設計，反而是這次 bug 的根源。順手把標題元件定義搬到模組層級，讓它們在每次渲染間身分穩定，不會被當成不同元件類型重新掛載。

### 目錄支援到 h4、下一篇文章可手動指定 nextSlug

使用者確認目錄修好後追加兩個延伸需求：一是目錄先前只認 h2/h3，問「之後如果有不同階級要怎麼呈現」，判斷是要順便把 h4 也接起來，`extractHeadings` 正則從 `#{2,3}` 放寬成 `#{2,4}`，`MarkdownContent` 補上 `h4` renderer，`TableOfContents.tsx` 改用 `indentByLevel` 對照表依階級縮排，之後真的出現 h4 不用再改程式碼。二是「下一篇文章可以指定，初始值一樣是照順序」——`Article` 新增 `nextSlug?: string`，`useNextArticle` 優先看目前文章有沒有指定 `nextSlug` 且該文章存在又已上架，沒有才 fallback 回預設的日期排序，對現有文章完全不影響。用這個欄位把 `exploring-hci.md`／`.en.md` 的下一篇指定成 `code-pulse-good-design`，讓這篇系列文章照寫作順序串接，而不是被日期排序打散。
