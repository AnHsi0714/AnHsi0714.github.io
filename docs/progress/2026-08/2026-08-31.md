新增 [KnowledgeGraph.tsx](../../../src/pages/knowledge/KnowledgeGraph.tsx)（路由 `/knowledge/graph`）：力導向布局是手寫的純數值版（節點互斥、邊當彈簧、同分類節點被拉往各自的分類錨點聚成一叢），同步跑固定 260 次迭代取最終位置渲染，不用 `requestAnimationFrame` 動畫，也沒有加 `d3-force` 之類的相依套件，方便看不順眼就整個砍掉。節點用一般 HTML 元素定位（不是 SVG `<text>`），標題不會有截斷或跑版的問題；只有邊用一層 SVG 畫。

預設只顯示 6 個分類的 hub 節點（各自標數量），點一個分類（畫布裡的 hub 或上方的 `Chip` 篩選列，兩者共用同一個 toggle）才展開成該分類底下的個別知識點，可以同時展開多個分類；跨分類的關聯線會依兩端目前是否展開，動態指向對方的實際節點或對方的分類 hub（`idFor()`），分類內部關聯收合時先不畫，避免自己連自己。展開／收合時用一個 `positionsRef` 快取上次算出的位置當作下次模擬的種子，已經在畫面上的節點不會整個重新洗牌，只有新出現的節點才從分類錨點附近的隨機點長出來，`left`／`top` 也加了 transition，用滑的過去而不是瞬間跳位。

節點支援用 Pointer Events 手動拖曳：拖曳中的位置蓋過模擬結果，放開後寫回 `positionsRef`，之後重新模擬會接著算而不是被蓋掉；用一個 `moved` flag 分辨「單純點一下」跟「拖曳後放開」，只有真的拖動過才在 `click` 時 `preventDefault()`，不然拖完會誤觸導頁或展開分類。拖曳中另外關掉 `left`／`top` 的 transition，不然節點會用 300ms 慢半拍跟著游標跑。

手機螢幕太窄不適合這種需要拖曳、平移的圖形介面，`sm`（640px）以下 `/knowledge/graph` 直接不渲染圖，只顯示一行文字請使用者改用平板或電腦；`/knowledge` 頁的入口連結也一併隱藏，不留一個點了沒用的死連結。先備知識的方向提示原本放在畫布下方，使用者反映應該放上面，一進頁面就看得到，改到分類 `Chip` 列上方。

分類 `Chip` 列直接複用站上既有的 `Chip` 元件（`selected` 樣式），一物兩用：展開狀態的視覺呈現兼分類色圖例。做完看過效果後決定保留，先不繼續往下做顏色區分不同關聯類型、行動版適配等更細的打磨。

### 新增 NgRx、RxJS 兩篇實習技術筆記

從實習用 Angular 接觸 NgRx／RxJS 的經驗出發，新增 [ngrx-state-management.md](../../../content/articles/zh/tech/ngrx-state-management.md) 與 [rxjs-flattening-operators.md](../../../content/articles/zh/tech/rxjs-flattening-operators.md)（皆含英文版），並在 knowledge.json／knowledge.en.json 補上對應詞條。NgRx 那篇先以完全新手視角重寫前情提要（一開始根本不知道 NgRx 在幹嘛，只看到好幾個元件都用到），核心概念、五個環節怎麼串起來的敘述維持不動；標成 `status: draft`，還沒要公開發布。

RxJS 那篇最初只涵蓋 concatMap／switchMap／mergeMap 三個 flattening operator，之後陸續擴充：

- 補上 exhaustMap 當第四個攤平策略，四個 operator 表格、結論同步更新。
- 一開始只給每個 operator 一個抽象範例（`trigger$.pipe(xxxMap(...))`，四個範例除了 operator 名稱外完全一樣），使用者指出這樣「看不出意思」，改成四個各自對應自己段落情境的具體範例（mergeMap：連續刪除多筆項目；concatMap：結帳三步驟；switchMap：搜尋框打字；exhaustMap：送出按鈕防連點），每段補一句輸入→輸出的具體說明。
- 加了一個「常用 operator 快速對照」段落，涵蓋 map／filter／tap／distinctUntilChanged／catchError／retry／forkJoin／take(1)／takeUntil 九個常用 operator。範例欄一開始也是抽象語法（`filter((n) => n > 0)` 這種），同樣被要求要看得出意思，改成統一套用 `users$` 情境、寫成「輸入 → operator → 輸出」的格式。
- forkJoin 補了一段實習時真實遇到的 code review 教訓：一開始把多支 API 包進同一個 forkJoin 平行拿資料，被提醒只要其中一個來源出錯就會整個失敗、其他已成功的結果也會被丟棄；後來改成每支 API 各自用 catchError 接住錯誤、給預設值，讓 forkJoin 保證會完成。這段內容也回頭寫進 `fork-join` 知識詞條的 `application` 欄位。
- 文末原本寫「這幾個沒有實際踩過坑，先當參考」，加了 forkJoin 後改成「攤平策略那四個和 forkJoin 是真的踩過坑的，其餘先當參考」。

NgRx 文章也陸續加了兩段：Signal（Angular 內建的反應式機制，跟 NgRx Store 處理不同範圍的狀態，判斷標準是「只有這個元件在乎，還是其他不相關元件也要讀」）、OnPush（Angular 的變更偵測效能優化，解釋了為什麼 Reducer 一定要回傳新物件而不能直接改，並點出這跟 RxJS 的 distinctUntilChanged 概念上很像，兩者預設都用 `===` 判斷「有沒有變」）。

### 知識點 application 依情境（專案／文章）分開顯示

原本 `application` 欄位是單一字串，同一個詞被多個專案共用時（例如 `cosine-similarity` 同時被 CodePulse、ABSA-WordCloud 引用）就把兩邊的用法寫成一句合併文字，不管從哪個專案頁點開都看到同一段混在一起的說明。改成 `application` 可以是 `string`，也可以是 `{ [專案或文章 slug]: 該情境下的說明 }`（[content.ts](../../../src/types/content.ts)）。

`MarkdownContent` 新增 `contextSlug` prop，[ProjectDetail.tsx](../../../src/pages/projects/ProjectDetail.tsx) 傳自己的 `project.slug`、[ArticleDetail.tsx](../../../src/pages/articles/ArticleDetail.tsx) 傳 `article.slug`，一路傳給內文裡的 `Term` 彈窗。新增 [resolveApplicationLines](../../../src/lib/knowledge.ts)：`application` 是物件時，對得上目前 `contextSlug` 的 key 才顯示那一句，對不上就不顯示；`application` 是單一字串時，檢查這個詞的 `relatedProjects`／`relatedArticles` 有沒有包含目前的 `contextSlug`，沒有就整個「在此專案中」區塊都不顯示（例如在 personal-website 專案頁的 Glossary 功能說明裡，拿 `ELO Rating`、`AST`、`Cosine Similarity`、`CKIP`、`Zero-Shot` 當範例列出，這幾個詞其實只在 CodePulse／ABSA-WordCloud 用到，跟 personal-website 無關，點開後就不會再顯示 CodePulse 的說明文字；`RLS` 因為在 personal-website 裡真的有自己的用法，`relatedProjects` 本來就包含 `personal-website`，所以會正常顯示）。沒有 `contextSlug`（獨立的 `/knowledge/:slug` 頁面）則維持顯示全部，不做情境篩選。`cosine-similarity`、`information-visualization`、`race-condition` 三個詞條的 `application` 改成物件形式，並拆出各自對應的分項說明文字。

### 首頁、About 頁補語意標題，全站色彩對比稽核

首頁把原本用樣式化 `<p>` 充當標題的地方（標題、各區塊標題、卡片標題，含 [FeaturedArticlesCarousel.tsx](../../../src/components/FeaturedArticlesCarousel.tsx)、[FeaturedProjectsCarousel.tsx](../../../src/components/FeaturedProjectsCarousel.tsx)、[Home.tsx](../../../src/pages/Home.tsx)）換成正確的 `<h1>`/`<h2>`/`<h3>`，讓螢幕閱讀器的標題導覽能正常運作。[About.tsx](../../../src/pages/about/About.tsx) 原本整頁沒有 `<h1>`（放大顯示的「About」/「Me」是一對 styled `<p>`），合併成單一 `<h1>`，段落標題也從 `<p>` 升級成 `<h2>`。研究興趣分類標籤、經歷年份標籤原本用 `text-muted` 疊 `opacity-80`，對比掉到 3.49:1 過不了 4.5:1，拿掉 opacity 後回到約 5.5:1。

全站色彩 token 對比稽核（新增 [design-audit skill](../../../.claude/skills/design-audit/SKILL.md) 記錄方法）：發現 success/info/danger 每個 token 其實身兼兩種角色卻共用同一個值，方向常常相反——Role A 是「文字/邊框直接印在頁面背景上」（outline Chip、Input 錯誤狀態），淺色模式要夠深、深色模式要夠亮；Role B 是「實心底配淺色文字」（Alert、Badge、filled Chip、按鈕），不分日夜模式都要固定夠深。拆成 `-outline`（分日夜模式各一版）跟 `-bg`（不分日夜模式，固定夠深）兩組 token 解決，outlineDanger、Alert 的 info/success/error、Badge 的 doing/done/success/danger、Chip 的 filled\* 系列原本都疊到 1.6～3.6:1，改完後全部過 4.5:1（或邊框用的 3:1）。

## 2026-09-05（六）

### 建了又拆掉的 /dev/contrast-checker 對比度檢查工具

一開始要比對 Badge/Chip/Card 樣式，新增 [ContrastChecker.tsx](../../../src/pages/dev/ContrastChecker.tsx)（路由 `dev/contrast-checker`）：可自選前景/背景色即時算 WCAG 對比度、對照 AA/AAA 門檻表，後來加上「測試對象」分類按鈕（中性/主色/進行中/完成/危險），選哪個類別就只覆寫該類別實際吃的那對 `--color-xxx` token，讓 Badge/Chip/專案卡片範例只有同色系的元件會跟著變色，方便對照。中途修正了一個真的 bug：`normalizeHex` 沒有轉小寫，`input[type=color]` 只吃小寫 `#rrggbb`，貼上大寫色碼時色盤會卡住不動。這個工具在後面色彩定案後就沒有用途了，連同路由一起刪除。

### 發現對話開始前已有一套沒被沿用的雙 token 架構

對話開始時 [theme.css](../../../src/styles/theme.css)、[tokens.scss](../../../src/styles/tokens.scss)、[Alert.module.scss](../../../src/components/Alert.module.scss)、[Button.module.scss](../../../src/components/Button.module.scss)、[Chip.module.scss](../../../src/components/Chip.module.scss) 就已經是未提交的修改狀態。比對已提交版本（`85317cf`，見 09-04 記錄）才發現：HEAD 裡本來就有一套拆好的雙 token 系統（`--color-danger-bg`／`--color-success-outline`／`--color-info-outline` 等），對話開始前的未提交改動已經把它合併回單一 token，猜測是使用者想換一套更簡單的顏色而先動手拆掉。跟使用者確認後，決定保留單一 token 架構、用這次談出來的新色，不用恢復舊的雙 token 版本。

### 顏色定案反覆：深色系被否決，中途一度又要拆回雙 token

先試了一組偏深的藍/綠/紅（`#325076`/`#235c46`/`#a80051`），跟主色 `#2f4f4f` 一樣是低彩度深色，視覺上悶成一片被使用者否決（「根本不能看」）；換成中彩度、稍亮的 `#19749f`/`#408000`/`#cd3c3c`，白字/深字對比都能過 4.5:1 才定案。

定案後使用者問深色模式的 Badge 文字能不能用白字：算出來深色模式三個底色都是刻意調亮給 outline Chip 用（要跟接近全黑的頁面背景比對比），亮度不夠深、白字疊上去只有 1.86～2.89:1，過不了。因為同一個 token 要同時滿足「填色底配白字」跟「outline 邊框疊在頁面上」兩種方向相反的需求，單一顏色沒辦法兩邊都顧到，於是把 token 拆回 `-bg`（實心底，不分日夜模式）／`-outline`（印在頁面上，分日夜模式各一版）雙軌，深色模式的填色文字才能重新用回白字。

### 綠色亮度、對比門檻的兩個提案都沒有採用

使用者問光模式的綠色 `#408000` 能不能再調亮：算出來這個值已經是「白字疊上去還能過 4.5:1」的天花板（margin 只剩 0.05），任何方向調亮都會掉到門檻以下；唯一能做的是保持亮度、把紅色分量拿掉換成更純的綠（例如 `#008400`），margin 幾乎不變但視覺更鮮明，這個方案提出後沒有被採用。使用者接著問能不能把門檻降到 4～4.5：說明 WCAG AA 對一般文字的門檻就是 4.5:1，沒有 4.0 這種中間級距，3:1 是留給大字級（18.66px 粗體以上）用的，Badge/Chip 這種小字不適用，降到 4~4.5 之間等同直接放棄合格，這個方向也沒有採用。

### 最終方案：拿掉所有實心底，Badge/Alert/Chip/Button.danger 統一改邊框

使用者提出真正解法：既然「填色配淺字」這個角色本身就是亮度天花板的來源，乾脆拿掉，Badge/Chip/Alert 全部改成邊框＋透明底（Chip 的 outline 樣式、Input 的錯誤狀態本來就是這樣）。因為 Badge、Alert 原本完全沒有邊框樣式（只有實心底），這不只是換顏色、是新增一組視覺樣式，所以先幫兩者加上 `tone="outline"` 選項、保留原本 filled 版本並存，在 [ComponentsPreview.tsx](../../../src/pages/dev/ComponentsPreview.tsx)（filled/outline 並排）跟 [Projects.tsx](../../../src/pages/projects/Projects.tsx) 的專案卡片狀態徽章（改 `tone="outline"` 直接在真實頁面預覽）上看過效果，確認可以接受後才拍板拿掉 filled、把 outline 變成唯一樣式。

同時把 [Button.module.scss](../../../src/components/Button.module.scss) 的 `.danger` 也一併改成邊框樣式（跟 Input 的錯誤狀態一致），並拿掉 `Badge`/`Alert`/`Chip` 的 `tone` prop 跟 `ChipTone` 型別——只剩一種樣式就不需要選了。token 系統也跟著收斂：`-bg`/`-text`/`-outline` 三組角色收回成一個（`--color-danger`/`--color-success`/`--color-info`），因為唯一剩下的角色就是「文字/邊框直接印在頁面背景上」，深/淺色模式各一版即可，不用再分兩種用途。順手清掉 [About.tsx](../../../src/pages/about/About.tsx) 技能標籤區塊裡因此變成恆真的三元判斷式，以及 [GalleryGrid.module.scss](../../../src/pages/gallery/GalleryGrid.module.scss) 裡一筆被連帶捲入、意外復原成舊值的 `--room-header-sub` 對比修正（`#75705f` 對 room-bg-2/3 只有 4.37/3.95:1，改回 `#6d6858`）。
