# NTUT FA Quest：有限自動機校園解謎遊戲

## 相關連結

GitHub：[ntut-fa-quest](https://github.com/AnHsi0714/ntut-fa-quest)

## 專案簡介

把北科校內的行政文件申請流程（跑導師簽名、系辦、教務處等）改寫成一款 2D 像素校園尋寶遊戲：玩家在地圖上跟不同單位的 NPC 互動、完成文件申請任務，過程中的行動序列會被記錄成一條 Trace，交給<span data-term="finite-automaton">有限自動機</span>驗證引擎判定是否符合合法流程，並顯示 ACCEPT / REJECT（附上反例）。

## 核心概念：把行政流程抽象成自動機

- 步驟順序固定的流程用 <span data-term="dfa">DFA</span> 建模
- 存在多種合法路徑的流程用 <span data-term="nfa">NFA</span> 建模
- 遊戲層只負責「決定發生什麼事件」（用時間、機率決定某個 NPC 現在在不在場），驗證層只負責「判斷這個事件在目前<span data-term="finite-automaton">自動機</span>狀態下合不合法」；時間與機率本身不進入形式語言，維持自動機定義的純粹性
- 採「事後驗證」而非即時攔截：玩家可以自由亂走、嘗試任何互動，不合法的轉移只會在 Trace 驗證時被標記，不會卡住玩家的移動，也就是「跑錯地方是可以的，只是流程不會過」

## 四份申請文件與對應自動機

- **文件 A（<span data-term="dfa">DFA</span>）**：導師 → 系辦 → 教務處，三步驟線性流程
- **文件 B（<span data-term="nfa">NFA</span>）**：四步驟流程中，中間兩步（系辦／系主任）可用 ε-transition 表示成任意順序完成
- **文件 C（PDA，尚未實作）**：加退選案例，規則是退選堂數必須全程大於等於加選堂數、送出時兩者相等，需要用堆疊做括號配對式的驗證，是典型的 Context-Free Language 案例，目前還沒學到這部分課程內容，先擱置
- **文件 D（NFA + Minimization，尚未實作）**：先印申請表和成績單（順序不拘），再由導師／社團指導老師／系上老師任一位簽名，三個簽名狀態在 minimize 後會因為後續路徑相同而合併成一個狀態，用來展示「行為等價」和「Trace 記錄」的差異

## 地圖與時間、體力系統

校園地圖從 22×17 擴大到 56×40 格，比照北科官方校園配置圖標示實際建築物位置，目前可進入的建築物包含科研大樓、一到四教學大樓、六教、共同科館、綜合科館、設計館、圖書館（B1～3F，各樓層服務分區依官網「樓層配置」頁面）、行政大樓（8 層，各行政單位樓層對照官網「行政單位」頁面），以及先鋒大樓（正式名稱先鋒國際研發大樓，位在忠孝東路對面，需要過馬路才到得了）。光華館 1、2 樓的「綠光庭園」餐廳則用來讓玩家恢復體力。

時間與體力系統用來避免玩家對著 NPC 乾等：部分 NPC 只在固定的上午或下午時段在場，部分 NPC（例如系主任）用機率決定是否在場、且只在時間推進時才重新擲骰；NPC 不在場時觸發的 `staff_absent` 事件因為沒有對應的合法轉移，會直接判定 REJECT，不需要額外設計「等待狀態」。上學時間為 08:00–20:00，體力耗盡會觸發用餐、上課等會消耗遊戲時間、但不進入 Trace 的支線任務。

## 目前進度

已完成 2D 像素校園地圖渲染、玩家移動與跟隨鏡頭、NPC 碰撞與對話系統，以及文件 A、B、D 三份流程本身的定義並整合進遊戲。剩下的部分，除了地圖與文件的收尾細節之外，主要卡在計畫書「軟體驗證目標」明列的兩塊自動機理論核心（PDA、<span data-term="dfa">DFA</span> Minimization），這兩塊做不完，驗證引擎的完整度就不夠。
